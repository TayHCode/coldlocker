### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean verification verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** One `delegate_task` owner per PR, in `mode: "async"`, on the live role selected for the work through `rules/model-routing.md`. Every brief stands alone: the owner gets only the brief, never your context. Always a fresh delegate per round; never resume-chain a brief. Use `t3_thread_launch` with a `workspaceStrategy` only when an owner needs its own thread and worktree. The `gh` CLI is the forge. Never require Graphite (`gt`). Each owner runs build, the first push, a ready PR linked with `link_pull_request` the moment it opens, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical review-bot triage, a slop-strip, a comment pass (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and comment pass, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with independent review. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Verify the planned behavior and required gates.** At the code-ready head, run the plan's self-run checks and any project-required independent review. Select coverage from changed behavior, with no fixed worker or audit count. Independent reviewers use the model and effort selected live for `auditor/verifier`, excluding every builder. A missing route is INCOMPLETE. Prove the changed behavior through the real surface when it exists, using the current harness's supported tools. Compare against trunk when it supports the scenario. The root audits the evidence and binds a PASS verdict to the exact head SHA before merge. A changed head needs affected checks rerun and a fresh review when project policy requires it.

   Return every proven finding to the owner with a reproducible case. Keep one writer per branch. Record pre-existing defects separately; do not silently waive regressions introduced by the PR.
5. **Merge only the verified head.** Finish any needed trunk integration before the final verdict. After a rebase, merge, or other head change, report the new SHA, rerun affected checks and obtain the required verdict bound to that exact SHA. Matching patch IDs never transfer a verdict across heads. Required forge checks must pass; never bypass them. Immediately before merging, fetch the live base and assess whether changes since verification affect the patch, its callers, dependencies or checks. If they do, integrate the current base, rerun affected checks and obtain a verdict bound to the resulting head. If they do not, record that assessment. Conflicts must be resolved and verified before merging. Use the forge's expected-head merge guard so a concurrent push cannot substitute an unreviewed head. Read back the merge commit and verify the shipped content. The owner merges only within the operator's authorization; operator-reserved items remain merge-ready.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, arm it with `schedule_task` on `{"type":"interval","everyMs":3600000}` with a prompt that runs this tick. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk and audit the operation against it. Fix drift during that tick. Probe each owner with `task_status` and `t3_thread_read`, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down with `task_cancel` and dispatch a replacement at once. Do not wait for a polite return. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose task cannot start a turn. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately, through `task_cancel` or a `t3_thread_interrupt`, and the scheduled audit tick is deleted. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the evidence supporting it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
